# PRD / 对话需求转 UI 工作流

本文件用于 0618 版新增需求场景：PM 直接提供 PRD、对话需求、功能说明或文档后，Codex 需要先分析需求，再基于原项目交互和设计生成前端页面或样式。

## 核心原则

- 不从 PRD 直接自由设计页面。
- 不把需求文档里的业务描述直接翻译成孤立 demo。
- 先理解业务流程，再匹配原项目模式，最后生成代码。
- 视觉一致只是底线，交互结构、组件选择、状态闭环和复用性同样重要。

## 步骤 1：提取需求结构

从 PRD 或对话中提取：

- 业务目标：需求要提升什么效率、解决什么问题或支撑什么流程。
- 用户角色：运营、管理员、销售、审核人、配置人、只读用户、AI 助手等。
- 主流程：进入页面、筛选对象、查看详情、编辑提交、审批确认、查看结果。
- 数据对象：项目、任务、客户、线索、工单、员工、Skill、权限、报表、日志、配置等。
- 页面类型：列表、详情、表单、看板、配置、流程、报表、日志、权限、抽屉、弹窗。
- 操作：新增、编辑、删除、批量、导入、导出、分配、提交、审批、驳回、撤回、复制、问 AI。
- 状态：草稿、待处理、处理中、已完成、异常、失败、禁用、无权限、过期、风险。
- 数据口径：指标定义、字段来源、筛选条件、时间范围、统计维度。
- 边界状态：空、加载、错误、无权限、校验失败、接口失败、批量部分成功、长文本溢出。

## 步骤 2：把业务语言映射成 UI 语言

使用以下默认映射：

| PRD 表达 | 默认 UI 模式 |
|---|---|
| 查询、检索、台账、管理、列表、记录 | 筛选栏 + 紧凑表格 + 分页 + 行内操作 |
| 新增、编辑、维护、配置 | 表单抽屉、表单弹窗或完整配置页 |
| 查看、详情、档案、画像 | 详情页头 + Tabs + 信息分组 + 时间线/活动记录 |
| 审批、提交、驳回、撤回、流转 | 状态条/动作栏 + 确认弹窗 + 审批记录 |
| 导入、导出、批量处理 | 工具栏按钮 + 进度反馈 + 结果明细 |
| 统计、趋势、分布、看板 | KPI 卡 + 图表 + 可下钻表格 |
| 风险、问题、异常、阻塞 | 等级标签 + 负责人 + 截止时间 + 处置动作 |
| 选择人员、部门、项目、客户 | 可搜索对象选择弹窗或抽屉 |
| AI 解读、总结、报告、复盘 | AI 结论卡 + Topbar AI 结果选择器 + 中间内容槽报告视图 |

## 步骤 3：形成 UI 实现契约

编码前必须明确：

- 页面采用哪种页型。
- 复用哪些已有页面或组件。
- 顶部页头如何表达当前任务。
- 筛选区有哪些字段，默认值是什么。
- 表格列、状态标签、行内操作、批量操作分别是什么。
- 新增/编辑/详情使用抽屉、弹窗还是独立页。
- 是否需要右侧 AI 助手参与，以及 AI 内容是否需要展开到中间内容槽。
- 空、加载、错误、无权限、校验失败和成功反馈如何处理。
- 是否新增交互；若新增，为什么旧交互不够用。
- 页面区块图：按顺序列出 PageHeader、Notice、Summary、FilterBar/ListWorkspace、MainContent、Pagination，并标出每条相邻边界的预期间距与唯一所有者。
- 列表页是否直接复用 `ListWorkspace`；同时含 KPI 摘要时是否使用 `SummaryList`，而不是让 PM POC 自由拼装。

## 步骤 4：实现顺序

1. 搜索原项目相似页面、组件和样式。
2. 读取目标页面附近源码、CSS token 和相关 reference。
3. 先复用页面骨架和组件结构。
4. 再填入 PRD 字段、操作、状态和业务文案。
5. 只有既有交互不能满足时才新增交互。
6. 对新增交互做共用性检查。
7. 交付前按 `prd-ui-acceptance-checklist.md` 自检。

## 不完整 PRD 的默认补全

当 PM 未明确说明时，按联想门户工作台默认规则补齐：

- 管理类数据默认使用表格，不使用卡片瀑布流。
- 复杂筛选超过 5 项时，优先使用筛选区折叠或高级筛选抽屉。
- 新增/编辑字段较少时使用弹窗；字段较多或分组明显时使用抽屉或完整表单页。
- 涉及状态变更、审批、删除、批量影响时必须有确认反馈。
- 所有列表页默认包含空、加载、错误和无权限状态。
- 所有表单默认包含校验、保存中、保存失败和成功反馈。
- 所有危险操作使用明确文案，不只写“确认操作”。

# 中间内容槽组件库

本组件库只治理顶部栏下方、左导航右侧、右 Agent 左侧的中间内容槽页面样式与结构。它不重新定义侧栏、Topbar、静态页签、AI 结果选择器、右侧 Agent、Composer 或其他封板壳层。

## 目录

1. 组件库组成
2. A/B/C 成熟度
3. 复用范围
4. AI 决策顺序
5. 升级、修改与退出

## 1. 组件库组成

中间内容槽页面由以下四部分组成：

```text
T1–T7 页面编排 + C 稳定组件 + B 孵化组件 + A 页面局部模式
```

- T1–T7 与 V1–V5 决定页面结构和业务流，不属于单个组件。
- B/C 组件必须在 `content-slot-component-registry.json` 登记，并可在 `assets/content-slot-component-library.html` 找到结构样例。
- A 不是共享组件，只是已存在或新生成的页面局部模式；保留在页面内部并登记观察。
- 组件使用 `design-tokens.md`，不得自建颜色、字号、圆角和通用间距体系。

## 2. A/B/C 成熟度

### A｜Candidate 页面局部模式

- 当前页面真实存在，但还没有稳定复用合同。
- 允许 AI 按业务需求创建和优化，但样式必须 page-local/scoped。
- 不进入共享组件目录，不宣称为全站标准，不要求邻页复制。
- 记录来源页面、业务任务、数据形态、状态、可能复用点和观察结论。

出现第二处相似模式只触发 B 阶段评估，不自动升级。视觉相同但任务、数据、交互或状态不同的结构继续保持 A，或只复用更低层的 Surface/Token。

例如“点击 KPI 过滤表格”只有在某个真实路由提出该需求后，才在该页面登记一个 A；不得为了预判未来需求，先在注册表中创建没有消费者的假组件。

### B｜Incubating 孵化组件

- 至少两个真实消费者承担相同任务，或单个高风险交互值得提前抽取。
- 已定义结构、数据输入、事件、slots/区域、状态、响应式和反例。
- 允许根据新的真实消费者调整 API，但每次都要列出影响页面并完成回归。
- 优先合并历史 class 方言，不通过业务布尔属性把多个页面硬塞进同一组件。

A 升 B 必须同时确认：

1. 用户任务相同。
2. 数据形态相近。
3. 交互、状态和响应式一致。
4. 抽取后不会形成大量 `isGmv`、`isTraffic`、`isLead` 等业务开关。
5. 至少两个页面完成结构与视觉对比；高风险单例需记录提前抽取理由。

### C｜Stable 稳定组件

- 结构、默认视觉、状态和响应式已经封顶，是新增页面的默认复用入口。
- 没有独立需求时不得随意改变默认行为或视觉。
- 单页差异优先使用已有 props/slots、页面组合或 Domain wrapper，不污染 Common 默认值。
- 允许修复 bug、无障碍、响应式、性能和 token 漂移；会改变消费者结果时必须做影响分析和回归。

B 升 C 必须满足：

- Common 至少跨两个业务域稳定使用；Domain 至少在域内两个页面稳定使用。
- 初始、加载、空、错误、无权限、禁用、成功、部分成功和过期状态按适用性完成。
- wide/squeezed、键盘、焦点和页面横向溢出完成验证。
- 不依赖新增全局覆盖或大量 `!important` 才能成立。
- API、锁定项、允许变体、消费者和退出路径已登记。

## 3. 复用范围

A/B/C 只表示成熟度；每项还必须登记独立复用范围：

- `Page-local`：一个页面内部使用。
- `Domain`：同一业务域的两个以上页面使用。
- `Common`：两个以上业务域使用。

成熟度与范围可以独立变化。例如 `C + Domain` 是稳定的领域组件，不代表可以全站使用；`B + Common` 是跨域孵化组件，仍允许调整 API。

A 默认只能登记为 `Page-local`。只有完成第二个真实消费者评估并形成复用合同后，才能在晋升 B 的同时改为 `Domain` 或 `Common`；不得用“未来可能复用”提前扩大范围。

## 4. AI 决策顺序

处理内容槽新需求时严格按以下顺序：

1. 使用现有 C 组件的默认能力。
2. 使用现有 B 组件，并检查当前消费者与允许变体。
3. 通过现有 props、slots 和多个组件组合承载需求。
4. 为单一业务建立 Domain wrapper，不修改 Common 默认行为。
5. 只有确属公共能力时，为 B/C 增加正式 variant，并记录全部消费者影响。
6. 完全无法合理承载时，在目标页面创建 A 模式并登记。

禁止：

- 因为视觉相似就跳过语义判断。
- 为一个页面给 Common 组件增加业务专属布尔开关。
- 将第一次出现的结构直接登记为 C。
- 修改 C 默认值后只验证提出需求的页面。
- 把 Skill 中的设计组件误报为项目已存在的共享 Vue 组件。

## 5. 升级、修改与退出

- `A → B`：满足真实复用或高风险条件，形成组件合同并补结构资产。
- `B → C`：满足消费者、状态、响应式和验收证据条件。
- `B → A`：长期只有一个消费者，或抽取后业务分支多于复用收益。
- `C → deprecated`：不再推荐新页面使用；列出替代组件和消费者迁移计划。
- 分裂：消费者语义明显分叉时，保留稳定基础组件并拆成 Domain wrapper。

C 组件变更分三级：

- Patch：bug、无障碍、token 漂移，不改变公开结果；完成消费者抽样回归。
- Compatible：增加可选 slot/variant，默认结果不变；完成全部新增路径和代表消费者回归。
- Breaking：默认视觉、结构、事件或数据合同变化；必须由明确需求授权，列出迁移和回退方案并验证所有消费者。

## 6. 登记与实现状态

以 `content-slot-component-registry.json` 为机器可读登记源。每项至少记录：

- ID、名称、成熟度、复用范围。
- 用户任务、来源页面、消费者。
- 数据形态、结构、状态、响应式、可配项、锁定项和反例。
- Skill 结构资产和 CSS 合同。
- 项目实现状态、源码位置和是否存在共享 Vue 组件。
- 升级条件、退出路径和验收状态。

A 允许先登记观察字段；B/C 必须补齐完整合同，或通过 `contractRefs` 指向已经封顶的数据形态、结构、事件、响应式和状态合同。缺少这些证据时不得把 B 升为 C，也不得把 Skill 成熟度解释为项目实现完成。

设计成熟度和项目实现状态必须分开：

- `skill-template`：Skill 中已有可复用结构和样式资产。
- `project-page-local`：项目仍由页面各自实现。
- `project-legacy-wrapper`：项目仍通过旧 HTML/runtime 套壳。
- `project-shared-vue`：项目已存在真实共享 Vue 组件。
- `project-mixed-unverified`：不同消费者实现方式不一致，尚未完成逐页源码核对；不得据此宣称已有共享组件。

只有同时满足 `projectImplementation: project-shared-vue`、`sharedVueComponent: true` 和实施验收门，才能宣称“项目已经组件化”；`project-mixed-unverified` 明确不能作为完成状态。

## 7. 页面生成规则

生成或优化内容槽页面时：

1. 先选择 T1–T7 主类型和必要的一个 V 变体。
2. 读取注册表，输出“直接复用 / 组合复用 / 需要扩展 / 新建 A”的判断。
3. PM 原型、AI 生成页面和研发新增需求都优先从 `assets/vue-content-slot-components/` 解析 B/C 组件；研发应先复用项目已有的同合同实现，再按需适配 Skill 参考源码。静态 HTML 只用于视觉核对。
4. 新建 A 时使用现有 token、C 基础组件和 scoped 样式，并登记来源和观察点。
5. 优化 B/C 前列出所有消费者、变更等级、视觉/行为影响、回退方式和验证范围。
6. 页面验收同时记录组件成熟度和项目实现状态；不得用组件登记替代运行证据。
7. 存在 KPI、时间、状态等联动筛选时，需求进入实现前必须明确数据作用域、条件组合关系、清除行为、时区/日期边界和“筛选变化统一回到第 1 页”；这些是业务合同，不由视觉组件猜测。
8. AI 结果页虽由动态页签打开，仍是中间内容槽页面：选择一个 T1–T7 主类型并叠加 V3，按相同 `C → B → 组合 → Domain wrapper → A` 顺序复用组件。动态页签的会话归属、切换、保存和关闭不进入 Common 组件。

## 8. 抽离批准与工程状态

`approved-for-planning` 只表示用户同意把候选纳入组件抽离计划，不改变 A/B/C 成熟度，也不证明项目已有共享 Vue 组件。

- 批准后先补消费者矩阵、统一 API、视觉差异和回退方案。
- 实施前仍需确认最终统一样式；UAT 是现状与业务行为来源，Skill token/合同用于解决页面间冲突。
- 只有源码落地、消费者迁移和回归通过后，才把 `projectImplementation` 改为 `project-shared-vue`、把 `sharedVueComponent` 改为 `true`。
- 未经新的实现授权，不修改 UAT、项目源码或线上样式。

## 9. Skill 组件库实现

用户已授权把批准候选写入设计 Skill。当前设计实现由三部分组成：

- `content-slot-component-contracts.md`：14 个独立工程合同的结构、设计 API、状态、响应式、锁定项和反例。
- `content-slot-component-registry.json`：机器可读的成熟度、复用范围、实施波次与项目实现真值。
- `assets/content-slot-component-library.html` + `assets/content-template.css`：可运行静态结构和状态预览。
- `assets/vue-content-slot-components/`：供 PM、UI、AI 和研发共同使用的 Vue 组件基线；使用方法见 `content-slot-vue-library.md`。

这一步将批准项标记为 `skill-library-implemented` 和 `skillVueComponent:true`，但仍保持 `sharedVueComponent:false`。前者只代表 Skill 中存在可复用 Vue 参考实现；后者继续表达研发项目尚未核验或落地。不得据此宣称 UAT 或项目页面已迁移。

## 10. Skill Vue 参考组件与项目源码边界

- Skill Vue 组件服务于 PM 原型、需求演示、AI 生成页面、研发新增需求和项目交付。PM/UI 默认写入独立原型；研发实施请求写入其明确范围内的目标项目。
- “使用设计 Skill”本身不授权项目写入；但用户要求在已识别项目中新增、修改或实现研发需求时，该请求已经授权正常的范围内源码编辑，无需再为组件库复用单独确认。
- 所有角色必须先读取注册表，按 `C → B → 组合 → Domain wrapper → A` 决策。已有组件能承载时直接复用；允许扩展时保持默认 API 兼容；完全不能承载时建立 A 并登记候选。
- AI 不得因为生成了新的 A 就自动把它加入共享组件目录。只有满足 A→B 或 B→C 证据门，并更新合同、预览、Vue 参考源码、注册表和一致性检查后，组件库才算新增。
- 研发先复用项目已有同合同组件；缺失时可复制、重写或映射 Skill 参考组件，但必须结合真实数据、工程框架和现有基础组件。Skill 参考实现不是可绕过研发评审的生产包。

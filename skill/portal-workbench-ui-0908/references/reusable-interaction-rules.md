# 新增交互共用性规则

本文件用于判断 PRD 新需求是否允许新增交互方式，以及新增后如何保证它能被后续类似需求复用。

通用业务内容槽中的查询、表格、表单、弹层、反馈和响应式行为先遵守 `content-slot-design-contract.md`。本文件只判断“是否值得新增一种交互模式”。

## 内容槽基础交互不得省略

以下不是页面可选装饰，而是相应场景的基础合同：

- 查询：明确手动查询或自动查询，`重置`恢复产品默认值，并定义是否立即重新查询。
- 高级筛选：展开/收起保留值；收起后显示隐藏条件数量或摘要。
- 分页：查询/排序后回到第 1 页；刷新尽量保持当前位置；删除到空页时回到有效页。
- 批量：显示已选数量，定义翻页/重新查询后的保留策略，危险操作说明影响范围并确认。
- 表单：失焦校验、提交全检、首错聚焦、防重复提交、失败保留输入、未保存离开确认。
- 弹层：焦点进入/返回、Escape/遮罩关闭策略、脏数据拦截和提交状态完整。
- 异步任务：排队、运行、部分成功、失败、取消、恢复、仅重试失败项均有明确状态。
- 页面反馈：持续状态用 StatusTag，分区问题用 Alert，短暂操作结果用 Toast，不混用。
- 状态连续：返回列表恢复筛选/排序/分页/滚动；可分享条件优先进入 route query。
- 响应式：按内容槽实际宽度降列，页面根无横向滚动，Agent 打开/关闭都验证。

AI改图／AI插图的校验、上传、审批和发布反馈还需读取 [AI商品管理反馈合同](ai-product-feedback-contract.md)，落实错误归属、结果失效、并发校验与首错定位。不得将该领域的物料／图片业务限制扩展到其他流程。

## 允许新增交互的条件

同时满足以下条件时，才允许新增交互：

- 原项目已有页面、组件和交互无法合理承载该需求。
- 使用旧交互会导致流程明显低效、信息不可读、状态不可表达或操作风险过高。
- 新交互能解决一类相似问题，而不是只服务当前页面。
- 新交互可以沉淀成共享组件、组合模式或明确设计约定。
- 新交互仍然使用原项目 token、密度、动效、状态和视觉层级。

## 不允许新增交互的情况

- 只是为了让页面看起来更丰富。
- 只是因为 PRD 没写清楚，实际可用既有模式承载。
- 只是单个页面、单个按钮、单个字段的临时样式。
- 会引入新的视觉系统、外部组件默认风格或与项目密度不一致的体验。
- 会破坏左侧导航、右侧 AI 助手、内容槽、页头或表格体系。

## 可复用交互命名

新增交互应能命名为以下类似模式：

- 高级筛选抽屉
- 批量操作确认
- 可编辑表格行
- 审批动作栏
- 状态流转面板
- 对象选择弹窗
- 时间线活动抽屉
- 多步骤配置向导
- AI 结构化报告页签
- 异步任务结果面板
- 导入结果明细弹窗
- 字段级变更对比面板

如果无法用这种方式命名，通常说明它还不是可复用交互。

## 设计要求

新增交互必须定义：

- 适用场景。
- 触发入口。
- 打开、关闭、确认、取消、失败、重试状态。
- 空、加载、错误、无权限、禁用状态。
- 与键盘焦点、可访问性、Toast、确认弹窗的关系。
- 与右侧 AI 助手、Topbar AI 结果选择器和中间内容槽 AI 结果视图的关系。
- 是否需要共享组件 props 或 CSS class。

## 沉淀规则

- 如果新交互只在单次探索中使用，先保持局部实现，但命名和结构要为复用预留。
- 如果同类需求预计会再次出现，优先抽象成共享组件或公共样式。
- 如果同类交互在真实页面中成功复用 3-5 次，应更新 `references/components.md` 或 `references/page-templates.md`。
- 更新规范时只记录稳定决策，不把临时试验写成全局规则。
